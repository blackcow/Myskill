# 05 工作流与系统形态

## 什么时候读

当讨论“应该做成 skill、workflow、工具服务还是独立 Agent”时，读这篇。

## 推荐形态

不要只做成一个 skill，也不要一开始做成完整独立产品。

推荐组合：

```text
Tech Radar Skill
  -> 定义判断流程、L0-L4 分级、技术卡片、认知资产沉淀格式

Source Tools
  -> 负责抓取公开网页、微信公众号、微信视频号、YouTube transcript、X / Twitter、arXiv、GitHub

Asset Wiki / Repo
  -> 保存 raw source、radar cards、认知资产、index、log

OpenClaw / Hermes Workflow
  -> 把上面三层串起来，形成可重复执行的 Agent 流程
```

一句话：

> skill 是脑子，工具是手，资产库是长期记忆，OpenClaw / Hermes workflow 是执行编排。

## 为什么不能只做成 skill

skill 适合定义工作协议：

- 怎么判断信息。
- 怎么分级。
- 怎么写技术卡片。
- 怎么决定是否进入资产库。

但以下内容不适合只放在 skill 里：

- 公开网页正文抽取、浏览器渲染和图片本地化。
- 微信公众号抓取。
- 微信视频号公开分享页抓取。
- YouTube transcript 获取。
- 论文 PDF / arXiv 解析。
- GitHub 仓库结构分析。
- X / Twitter 线程解析。
- 长期资产库索引和去重。
- 资产版本管理。

这些更适合作为工具服务、脚本或 connector。

## 当前已经落地的 Source Tools

当前可运行工具已经放在 `02_采集与归档方案` 中：

| 工具 | 输入 | 输出 | 状态 |
| --- | --- | --- | --- |
| 公开网页 Markdown 归档 | 普通公开网页 URL | `metadata.json`、`article.md`、`assets/` | 已验证，支持图片下载和 `--render-js`；正文开头保留必要 frontmatter |
| 微信公众号文章最小归档 | 微信公众号短链 | `metadata.json`、`article.md`、`assets/` | 已验证，支持图片本地化和运营尾巴清理；正文开头保留必要 frontmatter |
| YouTube 逐字稿原始字幕抓取 | YouTube URL 或 video id | `metadata.json`、`transcript.md`、`transcript.json`、`raw_transcript.txt`、`raw_transcript.json` | 已验证，支持原始字幕选择、分组逐字稿、括号内事件单独成组，以及收敛后的启发式 speaker 分组 |
| 论文 PDF 归档 | arXiv / PDF URL 或本地 PDF | `metadata.json`、`paper.md`、`paper.json`、`source.pdf`、`assets/` | 已验证，支持 Docling 解析、默认 `image_scale=4.0` 的图片资产原位引用、复杂矢量 Figure 整块裁剪回退、arXiv 元数据 fallback、pypdf 尾页兜底和原始 PDF 留存 |
| 微信视频号视频归档 | 微信视频号 `sph` 分享链接；可选本地视频/音频文件；可选 `--auto-download wx_channel` | `metadata.json`、`video.md`、`transcript.json`、`feed.json`、`source_media.<ext>`、`assets/` | 已验证，支持公开预览元数据和封面归档；已用 `wx_channel` 获取真实视频号 `mp4` 并通过 OpenRouter ASR 生成逐字稿；已支持 Agentic CLI 检查/启动微信 PC 和 `wx_channel`，并以结构化状态码记录未 ready 的微信侧前置条件 |

文章类来源统一使用 `article.md` 作为正文主文件。`structured`、`local`、抓取方式、图片本地化状态等实现细节不写进文件名，而是进入正文 frontmatter 和 `metadata.json`。

视频逐字稿来源统一使用 `transcript.md` 作为阅读主文件。原始字幕和分组结构化证据保留为 `raw_transcript.*` 和 `transcript.json`，不和阅读主文件混在一起。YouTube speaker 只来自显式标签或足够密集的通用 marker；少量 `>>` 与 `[laughter]`、`[applause]` 等事件不应生成 speaker，相关判断字段写入 `metadata.json`。

微信视频号 `sph` 来源统一使用 `metadata.json` 作为 Agent 入口，并使用 `video.md` 作为唯一阅读主文件。`transcript.json` 保存字幕状态、全文、分段、ASR 细节和 speaker 降级；原始公开接口响应保留为 `feed.json`，不要把视频文案误当成逐字稿。

微信视频号媒体获取拆成两层：脚本内置 Agentic CLI 编排，`wx_channel` 仍作为外部下载/解密工具，`res-downloader` 作为通用资源嗅探兜底。`wx_channel` 实测链路是本地 `2026` 端口读取作者搜索、视频列表和 Profile，本地 `2025` 端口触发 `batch_start` 下载并解密成本地 `mp4`。CLI 可以自动启动微信 PC 和 `wx_channel`，但仍要求微信账号已登录、代理证书已确认，并且视频号页面注入客户端 ready；失败时进入 `metadata.json.media_acquisition`，而不是把任务变成无输出失败。

论文 PDF 来源统一使用 `paper.md` 作为阅读主文件。图片资产默认按 `image_scale=4.0` 保留到 `assets/` 并在正文中原位引用；复杂矢量 Figure 如果被 Docling 拆成正文碎片，则优先按当前 caption 关联或最近邻 picture bbox 插入整块裁剪回退图，保持图片在前、图注在后的顺序，并清理图内标签。若 picture bbox 只覆盖多面板 Figure 的局部子图，回退范围可向上扩展同一 Figure 的坐标轴、图例、panel 标识和长类别标签，但必须以其它 caption 作为边界，避免跨图合并；没有 picture bbox 时只使用靠近 caption 的短文本图表簇触发回退，避免整页裁剪。结构化解析结果保留为 `paper.json`，原始证据保留为 `source.pdf`，解析降级、图片数量、图片 scale、等效 DPI、Figure 回退、pypdf 兜底页码和文件哈希进入 `metadata.json`。

## 推荐工作流

```text
用户输入链接 / 文本 / 仓库
-> Source Router 判断来源类型
-> Source Tool 抓取并生成标准归档目录
-> 若抓取失败或触发边界，要求用户补充原文 / 快照 / transcript
-> Tech Radar Skill 做分类、评分、L0-L4 分级
-> 生成 Radar Card
-> 用户确认或自动进入下一步
-> L4 写入 Asset Wiki
-> 更新 index.md / log.md
```

Source Tool 的输出不直接等于“可信正文”。进入评分前需要做轻量验收：

- 是否抓到了正文，而不是登录页、环境异常页或空壳。
- 图片、视频封面、字幕等辅助信息是否被本地化或明确保留链接。
- 是否记录了抓取方式、来源 URL、发布时间、资源数量和 warning。
- YouTube speaker 是否只是启发式；`generic_marker_count` 和 `generic_marker_alternation_enabled` 是否支持当前 speaker 结果；少量 `>>` 或括号内事件是否没有被误判为 speaker；没有字幕时是否明确降级。
- 微信视频号是否只把公开文案当作文案，是否明确记录无字幕轨、无公开视频/音频地址；`metadata.json` 是否记录 `canonical_source: "video.md"`、`agent_reading_order`、`file_roles` 和 `media_acquisition`；若执行 ASR，是否记录用户提供或外部工具获取的 `source_media`、ASR 模型、费用、切片时间戳、`transcript.json.text` 全文和 speaker 降级，并把逐字稿正文写入 `video.md`。当 `media_acquisition.status` 为 `NEED_WECHAT_LOGIN_OR_CHANNEL_PAGE` 等状态时，技术雷达流程应要求用户补齐微信客户端前置条件，而不是把公开文案当成逐字稿。
- PDF 解析是否有公式、表格、图片或 OCR 降级；图片资产是否本地化并能被 `paper.md` 引用；`metadata.json` 是否记录 `image_scale`、`image_effective_dpi` 和 `figure_fallback_count`；复杂 Figure 是否没有把坐标轴、图例、panel 标识或长类别标签散落进正文，回退图是否覆盖完整多面板 Figure、没有裁入页眉、logo、其它图或上方自然段落，且是否保持图片在前、图注在后；无 picture bbox 的页面是否没有整页上收；Docling 失败页是否有 pypdf 文本兜底；必要时是否能回查 `paper.json`、`assets/` 或 `source.pdf`。

## 数据层建议

建议把长期资产保存在 Markdown repo 中，便于：

- 人直接阅读。
- Agent 直接编辑。
- git 记录变化。
- index / log 做轻量导航。
- 未来接入搜索、RAG 或图谱。

建议目录后续可以讨论，不在当前文档中定死。

## OpenClaw / Hermes 中的存在方式

可以拆成四个层次：

- Skill：定义判断协议和输出格式。
- Workflow：编排一次信息处理流程。
- Tool：负责来源抓取、解析、转写、仓库分析。
- Asset Repo：保存长期认知资产。

## 第一版运行方式

第一版可以手动触发：

```text
用户丢一个链接
-> Source Router 识别来源
-> 调用对应 Source Tool 生成归档
-> Agent 基于归档主文件处理
-> 输出重要性分级和技术卡片
-> 用户决定是否沉淀
```

不需要一开始自动监控信息源。
