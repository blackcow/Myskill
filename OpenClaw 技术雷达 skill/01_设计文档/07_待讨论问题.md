# 07 待讨论问题

## 什么时候读

当要继续推进设计、但不想一次性加载全部文档时，读这篇。

## 1. 价值判断

- 它解决的是“资料太多”的问题，还是“判断成本太高”的问题？
- 它解决的是“没时间阅读”的问题，还是“阅读后难以转成判断和资产”的问题？
- 它的核心对象是链接、信息、技术判断，还是长期资产？
- 它是否能减少“收藏了但没看”的认知债务？

## 2. 注意力分级

- L3 和 L4 的边界是什么？
- 什么信息只是值得深读？
- 什么信息值得进入长期认知资产库？
- 哪些内容必须忽略，即使它在社区很热？
- 哪些内容一旦出现，就应该自动进入重点关注？

## 3. 输入来源

- 第一版已能覆盖公开网页、微信公众号短链、YouTube 已有 transcript、论文 PDF / arXiv、微信视频号 `sph` 公开分享页；下一步是否优先补 GitHub 的专用解析？
- 微信公众号自动归档失败时，手工复制原文、网页快照、只保存标题链接三种降级方式如何排序？
- 微信视频号已经建立“`wx_channel`/用户提供媒体文件后 OpenRouter ASR”的增强链路；下一步是否需要补更精细时间戳、diarization 或多模态画面理解？
- X / Twitter 是先处理外链，还是也处理线程？
- YouTube 无字幕视频是否进入后续 ASR 能力，还是继续要求用户提供 transcript？
- YouTube 启发式 speaker 当前已收窄为“显式标签或足够密集的通用 marker”才启用；未来是否需要 WhisperX / pyannote 等真实 diarization？
- 对语言码和正文语言不一致的字幕轨，是否需要额外做语言检测并写入归档元数据？

## 4. 资产沉淀

- 资产库用 Markdown repo 是否足够？
- 认知资产应该按主题组织，还是按问题组织？
- 技术卡片和认知资产是否分开存放？
- L3 信息是否进入资产库，还是只保留卡片？
- 如何记录“这个判断后来被修正了”？

## 5. 系统形态

- Tech Radar Skill 应该包含哪些规则？
- 已落地的 Source Tools 如何接入统一 Source Router？
- Source Tool 的失败、warning、partial extraction 如何反馈给技术雷达评分流程？
- Asset Wiki 是否沿用 Karpathy LLM Wiki 的 raw / wiki / schema 思路？
- OpenClaw / Hermes workflow 先手动触发，还是一开始就自动编排？
- 是否需要独立 Agent，还是先作为 workflow 能力存在？

## 6. MVP 决策

- 第一版最有价值的输出是重要性分级、技术卡片、认知资产条目，还是 POC backlog？
- 第一版是否只做五个核心方向？
- 第一版是否允许用户人工确认分类和评分？
- 第一版如何证明它真的降低了认知负担？

## 7. 下一步建议

建议下一轮优先讨论：

1. L3 / L4 的判定边界。
2. 技术卡片和认知资产的最小字段。
3. Source Router 和已落地 Source Tools 的统一调用协议。
4. 第一版是否采用 Markdown repo 作为资产库。
5. OpenClaw / Hermes 中 v1 到底以 skill 还是 workflow 为主入口。
