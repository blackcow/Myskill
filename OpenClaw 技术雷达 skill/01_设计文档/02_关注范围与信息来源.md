# 02 关注范围与信息来源

## 什么时候读

当讨论“什么信息应该进入技术雷达”“不同来源怎么处理”时，读这篇。

## 核心关注方向

技术雷达 Agent 只围绕用户当前主线筛选和沉淀，不追逐泛泛的 AI 热点。

当前核心方向：

- Agent 和 Harness 框架，例如 OpenClaw、Hermes 等。
- Palantir 的本体论。
- 大模型训练。
- 应用 evaluation。
- 企业交付智能化。

## 不追求泛覆盖

不建议第一版做成“所有 AI 新闻都收”的聚合工具。

需要降级或忽略的信息包括：

- 社区很热但和当前主线无关的内容。
- 只有观点没有证据的内容。
- 只适合娱乐消费、不改变技术理解的内容。
- 重复传播、没有新增信息的二手摘要。

## 信息来源

### 文章链接

- 微信公众号文章链接。
- X / Twitter 上的文章、线程或外链。
- arXiv 上的论文。
- 普通网页文章和技术博客。

### 代码仓库

- GitHub 仓库。
- GitHub README。
- GitHub docs。
- GitHub release。
- GitHub issue / PR 讨论。

### 视频内容

- YouTube 长视频。
- 微信视频号公开分享视频。
- 技术博客视频。
- 访谈。
- 发布会。
- 教程。

## 当前已验证的解析能力

当前已经从“概念设计”推进到部分来源可自动归档。第一版不再只依赖手工复制正文。

| 来源 | 当前能力 | 输出主文件 | 元数据文件 | 关键边界 |
| --- | --- | --- | --- | --- |
| 公开普通网页 | 已实现自动归档，支持正文抽取、元数据、图片本地化、必要时浏览器渲染 | `article.md` | `metadata.json` | 不绕过登录、付费墙、验证码；动态页仍可能需要站点专用规则 |
| 微信公众号短链 | 已验证可用真实浏览器 UA 自动抓取，优先 `#js_content`，兜底 `content_noencode`，下载图片到本地，清理公众号运营尾巴 | `article.md` | `metadata.json` | 不处理登录、付费、验证码、被删除文章；反爬策略可能变化 |
| YouTube transcript/caption | 已实现原始字幕轨选择，避免自动翻译轨，按视频目录输出原始字幕和分组逐字稿；speaker 只来自显式标签或足够密集的通用 marker | `transcript.md` | `metadata.json` / `transcript.json` / `raw_transcript.json` | 只处理 YouTube 已暴露字幕轨；无字幕时不下载音频转写；少量 `>>` 和括号内事件不生成假 speaker |
| 论文 PDF / arXiv | 已实现 PDF 下载、Docling 解析、Markdown 阅读主文件、高分辨率图片资产原位引用、复杂 Figure 整块裁剪回退、结构化 JSON、原始 PDF 留存和 pypdf 尾页兜底 | `paper.md` | `metadata.json` / `paper.json` | 第一版面向文本型学术 PDF；默认关闭 OCR 和图片语义理解，图片资产默认 `image_scale=4.0`，复杂 Figure 会尽量避免图内标签污染正文，公式、复杂表格和图片仍需回查结构化 JSON、图片资产或原 PDF |
| 微信视频号 `sph` 分享页 | 已实现公开预览接口归档，保存作者、日期、文案、封面、头像、互动数和原始接口响应；已验证 `wx_channel` 可在微信 PC 端打开视频号页面后取得并解密本地 `mp4`，再用 OpenRouter ASR 生成真实逐字稿；脚本已支持 `--auto-download wx_channel --ensure-service` 的 Agentic 调用路径 | `video.md` | `metadata.json` / `transcript.json` / `feed.json` | 公开 `sph` 页面未暴露字幕轨、音频地址或可下载视频地址；媒体获取仍依赖微信 PC 登录态、代理证书和 ready 的视频号页面注入客户端；OpenRouter ASR 不提供真实说话人分离 |

## 来源处理难度

| 来源 | 自动化难度 | 第一版建议 |
| --- | --- | --- |
| 普通网页文章 | 中 | 支持 |
| arXiv / PDF 论文 | 低到中 | 支持 PDF 自动归档；保留原始 PDF 作为证据源 |
| GitHub 仓库 | 中 | 支持 README / docs / release 优先 |
| 微信公众号 | 中到高 | 支持短链自动归档；失败时允许手工复制原文或网页快照 |
| 微信视频号 | 中到高 | 支持 `sph` 公开分享页的元数据和封面归档；用户提供媒体或 `--auto-download wx_channel` 取得媒体时半自动支持 OpenRouter ASR |
| X / Twitter | 中到高 | 先处理单条内容和外链，不急于完整线程 |
| YouTube | 中 | 支持已有 transcript/caption；音频转写不作为 MVP 核心 |

## 微信公众号处理原则

微信公众号文章已经可以作为第一版自动归档来源，但仍不能把“所有文章都完全自动成功”作为成功条件。

当前主路径：

```text
微信公众号短链
-> 真实浏览器 User-Agent 抓取 HTML
-> 优先抽取 #js_content
-> 兜底抽取 content_noencode
-> 下载正文图片到 assets/
-> 清理 profile / script / iframe / 运营尾巴
-> 输出 article.md
-> 输出 metadata.json
```

可接受降级方案：

- 用户手工复制正文。
- 用户保存网页快照。
- 浏览器辅助抓取。
- 只保存标题、链接、摘要和手工补充的关键段落。

已验证测试用例见：[微信公众号文章测试用例](../04_测试用例/03_微信公众号文章/README.md)。

## YouTube 处理原则

YouTube 长视频中“已有 transcript/caption 的视频”可以进入第一版；“无字幕视频的音频转写”仍不作为核心能力。

优先级：

1. 有 transcript/caption 时抓取原始字幕轨，避免 YouTube 自动翻译轨。
2. 同时保留原始逐条字幕、按句子/时间合并后的阅读版和分组结构化 JSON。
3. `主持人：`、`嘉宾：`、`Host:`、`Guest:` 等显式标签可以启发式标记 speaker。
4. 行首 `>>` 或 `- ` 只有在同一字幕中足够密集时才启用轮换式 speaker；少量 marker 只清理符号，不硬猜 speaker。
5. `[music]`、`[laughter]`、`[applause]`、`[screaming]` 等括号内非语音事件单独成组，不参与 speaker 轮换。
6. 如果没有可靠 speaker 标记，不硬猜对话者，只做分组。
7. 无 transcript/caption 时先记录为 L1 / L2 信号，音频 ASR 作为后续增强能力。

需要特别注意：

- YouTube 返回的 `language_code` 不总是等同于正文真实语言，要结合正文样本判断。
- 原始字幕通常没有结构化 speaker 字段；当前 speaker 结果只是启发式，不是真实 diarization。
- `metadata.json` 和 `transcript.json` 中的 `speaker_markers_found`、`generic_marker_count`、`generic_marker_alternation_enabled` 是判断 speaker 可信度的关键字段。

已验证测试用例见：[YouTube 逐字稿测试用例](../04_测试用例/02_youtube逐字稿/README.md)。

## 微信视频号处理原则

微信视频号 `sph` 公开分享页可以进入第一版，但能力边界和 YouTube 不一样：公开网页端通常只给预览信息，不给字幕轨和视频源。字幕生成不走“解析官方字幕”，而走“本地媒体获取后 ASR”的增强链路；媒体可以由用户手工提供，也可以由脚本通过 `--auto-download wx_channel` 调用本机工具尝试获取。

当前主路径：

```text
微信视频号 sph 链接
-> 解析 short_uri
-> 调用 finder-preview get_feed_info 公开接口
-> 下载封面、头像、认证图标到 assets/
-> 输出 video.md
-> 输出 transcript.json 的字幕状态
-> 输出 feed.json 原始响应
-> 输出 metadata.json
```

增强链路：

```text
用户用外部工具获取本地视频/音频，或脚本通过 --auto-download wx_channel 触发本地下载
-> 复制或规范化为 source_media.<ext>
-> ffmpeg / imageio-ffmpeg 抽取音频切片到 assets/audio/
-> OpenRouter audio transcriptions
-> 输出 transcript.json 的结构化 ASR 逐字稿，并把逐字稿正文写入 video.md
-> metadata.json 记录 ASR 模型、费用、切片数、warning 和说话人状态
```

处理原则：

1. `metadata.json` 是 Agent 默认入口，必须记录 `canonical_source: "video.md"`、`agent_reading_order` 和 `file_roles`。
2. `video.md` 是唯一阅读主文件，保存作者、发布时间、文案、互动数、本地封面和字幕状态；ASR 或人工字幕成功时，逐字稿正文也写入 `video.md` 的“逐字稿”章节。
3. `transcript.json` 保存字幕状态、全文、分段、ASR 元数据和 speaker 降级；没有公开字幕轨时，`segments` 为空且状态明确为不可用。
4. `metadata.json.warnings` 必须写明“无字幕轨”和“无公开视频/音频地址”，避免后续 Agent 误以为已经转写。
5. 如果用户通过外部工具或手工提供原始视频/音频文件，可以显式开启 `--asr openrouter`，默认模型为 `openai/gpt-4o-mini-transcribe`；高价值视频可切到 `openai/gpt-4o-transcribe`。
6. ASR 输出的时间戳是按切片生成的近似边界；OpenRouter transcription 当前不提供说话人分离，不能把 `speaker` 当作真实身份。
7. ASR 必须记录模型、语言、费用、切片数、全文 `transcript.json.text` 和 warning；技术词应通过 `--asr-context` 或自动上下文提示降低误识别，并对英文术语做保守大小写归一。
8. 作者主页和更多视频列表需要微信内打开，公开网页端没有稳定更多视频接口；测试用例应优先使用用户实际分享的 `sph` 短链。
9. 媒体获取层当前首选 `wx_channel`，通用兜底为 `res-downloader`；`wx_channel` 实测可通过本地 `2025/2026` 端口读取作者搜索、视频列表、Profile 和批量下载状态。脚本可自动检查/启动微信 PC 和 `wx_channel`，但不能绕过登录态、扫码、代理证书或页面注入失败；这些状态必须进入 `metadata.json.media_acquisition`。
10. `wx_channel` 下载得到的通常是微信可播放转码版本，可能小于 Profile 中标注的原始 `fileSize`；本地媒体验收以实际 `source_media`、时长和可抽音频为准。
11. Agentic 调用失败时不应直接无产物退出；应保留公开页归档，并将 `WX_CHANNEL_NOT_RUNNING`、`NEED_WECHAT_LOGIN_OR_CHANNEL_PAGE`、`FEED_MATCH_FAILED`、`DOWNLOAD_FAILED` 等状态写入 `metadata.json.media_acquisition`。

已验证测试用例见：[微信视频号视频测试用例](../04_测试用例/05_微信视频号视频/README.md)。

## 论文 PDF 处理原则

论文 PDF 和 arXiv 链接可以进入第一版自动归档。当前主路径：

```text
论文 PDF / arXiv URL
-> 下载或复制 source.pdf
-> 使用 Docling 解析 PDF
-> 按默认 image_scale=4.0 导出图片到 assets/ 并在 paper.md 原位引用
-> 对复杂矢量 Figure 触发整块裁剪回退，清理散落进正文的图内标签
-> Docling pipeline 降级时追加 pypdf 尾页文本兜底
-> 输出 paper.md
-> 输出 paper.json
-> 输出 metadata.json
-> 保留 source.pdf 和 assets/
```

处理原则：

1. `paper.md` 是唯一阅读主源，适合摘要、问答、技术雷达打分和技术卡片。
2. `assets/` 保留 PDF 中的图片资产，默认以 `image_scale=4.0` 生成，`paper.md` 用本地相对路径原位引用，后续问答可按需把图片交给多模态模型理解。
3. `paper.json` 保留 Docling 结构化结果，用于回查章节、页码、表格、图注和证据块。
4. `source.pdf` 是最终原始证据，解析质量存疑时必须回查。
5. 默认关闭 OCR、图片描述、图表抽取和公式增强，避免 born-digital 论文解析时引入额外慢路径；这些边界应写入 `metadata.json.warnings`。
6. OCR 不进入默认链路。只有扫描版 PDF、图片文字需要索引或用户明确要求时，才单独生成 OCR 输出，不应混入 `paper.md` 主正文。
7. 如果 Docling 对部分页面失败，应写入 warning，并用 pypdf 追加尾页文本兜底；兜底文本只保证可读，不保证表格结构。
8. 如果 Docling 把复杂矢量 Figure 的坐标轴、图例、panel 标识、流程框文字或长类别标签拆成普通正文，应按同页 caption 和 bbox 渲染整块 Figure 回退图；有 picture bbox 时优先使用与当前 caption 结构关联或最近邻的图区锚点，并向下延伸到 caption 上缘以保留必要子图说明；如果 picture bbox 只覆盖多面板 Figure 的局部子图，可以向上吸收同一 Figure 的图表标签，但必须以同页其它 caption 作为边界，避免跨图或带入页眉、logo、上方自然段落；无 picture bbox 时只允许用靠近 caption 的短文本图表簇触发回退，宁可不触发也不整页上收；在 `paper.md` 中保持图片在前、caption 在后的顺序，清理正文碎片，并在 `metadata.json.figure_fallbacks` 记录页码、裁剪框和 warning。
9. 图片解析质量需要同时看 `metadata.json.image_scale`、`image_effective_dpi`、`figure_fallback_count` 和 `assets/` 实际像素尺寸；小图标可以保留，但不能代表论文主图质量。
