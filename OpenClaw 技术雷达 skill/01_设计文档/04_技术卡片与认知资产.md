# 04 技术卡片与认知资产

## 什么时候读

当讨论“怎么把一条信息变成个人认知资产”时，读这篇。

## 核心关系

技术雷达和 LLM Wiki / 认知资产库的关系是：

```text
技术雷达负责把信息变成判断
LLM Wiki / 资产库负责把判断变成长期认知资产
```

因此第一版不应该把所有输入都写进资产库。

只有 L4 信息，或者少数需要持续观察的 L3 信息，才进入资产沉淀。

## 单条技术卡片格式

每条 L2 以上信息可以生成技术卡片。

建议格式：

```markdown
# 技术卡片：标题

## 基本信息

- 来源：
- 链接：
- 作者 / 机构：
- 发布时间：
- 信息类型：文章 / 论文 / GitHub / 视频 / 社媒
- 所属方向：
- 重要性等级：L0-L4

## 归档与解析信息

- 归档目录：
- 正文主文件：
- 抓取 / 解析方式：
- 本地资源数：
- 解析警告：
- 降级说明：

## 一句话判断

用一句话说明这条信息为什么值得或不值得投入注意力。

## 核心观点

- 观点 1
- 观点 2
- 观点 3

## 关键证据

- 证据 1
- 证据 2
- 证据 3

## 与我当前认知的关系

- 它补齐了什么？
- 它挑战了什么？
- 它验证了什么？
- 它和已有资产有什么关联？

## 风险和不确定性

- 不确定点 1
- 不确定点 2

## 推荐处理

- 忽略 / 记录 / 短读 / 深读 / 沉淀 / POC

## 可沉淀资产

- 技术判断：
- 认知模型：
- 架构原则：
- 评测项：
- POC 候选：
```

## 来源证据要求

技术卡片不应只基于聊天上下文或临时摘要生成，应优先引用来源工具产出的主文件：

- 公开网页：优先读取 `article.md`，必要元数据在文件开头 frontmatter；完整抓取元数据和 warning 读取 `metadata.json`。
- 微信公众号：优先读取 `article.md`，必要元数据在文件开头 frontmatter；完整抓取元数据读取 `metadata.json`，并检查是否有远程图片、iframe、script 或运营尾巴残留。
- YouTube：优先读取 `transcript.md` 做阅读和判断；需要精确时间戳、speaker 轮次或片段级证据时读取 `transcript.json` / `raw_transcript.json`，轨道选择和解析状态读取 `metadata.json`。如果需要引用 speaker 结果，必须同时检查 `speaker_markers_found`、`generic_marker_count`、`generic_marker_alternation_enabled` 和 `groups[*].speaker_confidence`；括号内事件不能当作说话人证据。
- 论文 PDF / arXiv：优先读取 `paper.md` 做阅读和判断；图片会以 `assets/...png` 形式在正文中原位引用，默认按 `image_scale=4.0` 生成，复杂矢量 Figure 可能替换为 `figure_fallback_page_*.png` 整块裁剪图。回退图应优先按当前 caption 关联或最近邻 picture bbox 裁剪；当 picture bbox 只覆盖多面板 Figure 的局部子图时，可以向上扩展同一 Figure 的图表标签，但必须以其它 caption 为边界，避免裁入页眉、logo、其它图或上方自然段落；Markdown 中应保持图片在前、图注在后的顺序，后续问答可按需交给多模态模型；需要结构化证据时读取 `paper.json`，需要核对原文版面、公式、图表时回查 `source.pdf`，解析状态、图片数量、图片 scale、等效 DPI、Figure 回退、pypdf 尾页兜底和降级 warning 读取 `metadata.json`。
- 微信视频号：默认先读 `metadata.json` 判断 `canonical_source`、`agent_reading_order`、`file_roles`、`media_acquisition` 和解析状态，再读取 `video.md` 做元数据、文案、封面和逐字稿正文判断；`transcript.json` 只在需要全文、分段、近似时间戳、ASR 模型、费用、speaker 降级或 warning 时读取；公开视频号预览接口响应保留在 `feed.json`，仅用于溯源和 debug。若 `media_acquisition.status` 是 `NEED_WECHAT_LOGIN_OR_CHANNEL_PAGE`、`CONTACT_SEARCH_FAILED`、`FEED_MATCH_FAILED` 或 `DOWNLOAD_FAILED`，技术卡片只能引用公开视频文案，不能把它当作真实逐字稿。

如果来源工具标记了 warning、partial extraction、无字幕、speaker heuristic、`generic_marker_alternation_enabled=false` 等状态，技术卡片必须在“风险和不确定性”中写明，避免把解析结果误当成完全可靠的原始事实。

## 认知资产格式

L4 信息进入认知资产库时，不只是保存摘要，而是保存“可复用判断”。

建议格式：

```markdown
# 认知资产：判断标题

## 结论

一句话写清楚沉淀下来的判断。

## 适用范围

这个判断适用于哪些技术问题、场景或决策。

## 形成来源

- 来源 1
- 来源 2
- 相关技术卡片

## 推理依据

- 证据 1
- 证据 2
- 证据 3

## 对我认知的增量

说明它改变、补充或稳定了什么理解。

## 可复用方式

- 后续选型时引用。
- 后续评测时转成评测项。
- 后续 POC 时转成实验假设。
- 后续平台设计时转成架构原则。

## 仍需验证

- 待验证点 1
- 待验证点 2
```

## 资产库类型

长期资产库可以沉淀：

- 技术判断。
- 架构原则。
- 评测项。
- 工具选型依据。
- POC 候选。
- 路线候选。
- 企业交付智能化素材。
- 个人认知模型。
- 技术理解框架。

## 与 Karpathy LLM Wiki 的关系

相似点：

- 都反对临时摘要和一次性问答。
- 都强调长期沉淀。
- 都适合用 Markdown、index、log、引用证据和持续维护。

区别：

- 技术雷达是入口层，判断哪些信息值得进入资产系统。
- LLM Wiki 是沉淀层，负责组织、关联和维护长期资产。

推荐顺序：

```text
先信息过滤
再重要性分级
再技术卡片
最后认知资产沉淀
```
